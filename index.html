Introdução

Para quem é este livro, a ideia que ele defende e como cada capítulo funciona.

Você já sabe fazer uma página reagir a um clique. Este livro trata do passo seguinte: fazer uma aplicação inteira continuar certa quando ela tiver trinta telas, várias pessoas no código e um agente de IA escrevendo boa parte dele.

É para quem já constrói páginas com HTML, CSS e JavaScript, manipula o DOM, consome uma API com fetch e já escreveu um backend REST com Express e TypeScript. Nada disso é ensinado de novo. Se você cursa TEC.1052, guarde por perto o front-end do Mini-Prontuário que escreveu em JavaScript puro: ele é o ponto de partida do capítulo 1.

A tela é uma função do estado. Quase todo bug de front-end é um estado guardado no lugar errado, duplicado ou sincronizado à mão.

Por isso o livro não é uma lista de APIs do React. Cada capítulo responde, de um ângulo diferente, a uma pergunta: onde este estado mora?

Parte I · A mudança de paradigma
01

Do DOM à mão às interfaces reativas

O trabalho de manter a tela em dia com os dados não some quando você adota React. Ele muda de dono.

Terça, 14h. A enfermeira dá alta para Maria Souza, paciente de alto risco da Ala B. A linha some, o total cai de 6 para 5, e o painel continua dizendo: alto risco: 2.

Ninguém escreveu um erro; escreveram uma atualização a menos. A tela tinha três lugares que dependiam da mesma lista, e o código da alta lembrou de dois.

1.1Como chegamos aqui

Em 2005, o AJAX deixou a página pedir dados sem recarregar. Em 2006, o jQuery tornou a manipulação do DOM o jeito padrão de programar a tela. Em 2010, Backbone e AngularJS popularizaram as aplicações de página única. Em 2013 veio o React, com uma ideia diferente: a pergunta deixou de ser como alterar a tela quando um dado muda e passou a ser como a tela deve ficar para um estado qualquer. Vue e Svelte seguiram a mesma ideia com outra mecânica, e em 2026 o React passou a ser mantido pela React Foundation, na Linux Foundation.

1.2A Ala B em três versões

O laboratório está em laboratorio/cap01, na tag cap01: três páginas com a mesma tela, sem build. Seis pacientes fictícios, uma busca, um campo de anotação e um botão de alta por paciente, e um resumo com o total e quantos são de alto risco. Sirva a pasta com npx serve laboratorio/cap01 e abra cada página.

Cada uma traz no topo um medidor, um MutationObserver que conta os elementos que entram e saem do DOM e os textos ou atributos trocados. É ele que transforma "o React é eficiente" em número.

1.3Versão 1: você diz como mudar

A primeira versão é imperativa: o código dá ordens ao DOM, passo a passo. Na montagem ele preenche o total e o alto risco; na alta, remove a linha e corrige o total:

1-imperativo.html · altacap01
// alta: tira a linha e corrige o total
lista.addEventListener("click", (e) => {

  const li = e.target.closest("li");
  pacientes = pacientes
    .filter((p) => p.id !== li.dataset.id);

O código precisa saber quais nós existem, quais dependem de pacientes e em que ordem atualizá-los. Com três dependências já houve esquecimento; uma tela real tem dezenas.

1.4Versão 2: estado e render()

A segunda versão é a que a disciplina ensinou: um objeto estado e uma função que redesenha a tela inteira a partir dele.

2-render.html · render()cap01
// a tela inteira sai do estado, sempre
function render() {
  const t = estado.busca.toLowerCase();
  const vis = estado.pacientes.filter((p) =>
    p.nome.toLowerCase().includes(t));
  const alto = estado.pacientes
    .filter((p) => p.risco === "alto").length;
  app.innerHTML = `
    <p>${estado.pacientes.length} pacientes
      · alto risco: ${alto}</p>
    <ul>${vis.map((p) => `
      <li data-id="${p.id}">
        <b>${p.nome}</b> ${p.leito}
        <input placeholder="anotação">
        <button>Alta</button>
      </li>`).join("")}
    </ul>`;
}

Ela já pensa do jeito certo: o alto risco é calculado a cada render e nunca fica errado. O problema é o innerHTML, que joga fora todos os nós e cria outros. Cada tecla na busca reconstrói a lista, e o que estava dentro dos nós antigos vai junto: o texto das anotações, o foco.

1.5Versão 3: React

A terceira mantém a ideia da segunda e troca o mecanismo. O React vem do esm.sh por um importmap:

3-react.html · Alacap01
// a tela é uma função do estado
function Ala() {
  const [busca, setBusca] = useState("");
  const [pacientes, setPacientes] =
    useState(PACIENTES);

  const t = busca.toLowerCase();
  const vis = pacientes.filter((p) =>
    p.nome.toLowerCase().includes(t));
  const alto = pacientes
    .filter((p) => p.risco === "alto").length;
  const alta = (id) => setPacientes(
    pacientes.filter((p) => p.id !== id));

  return h("div", null,
    h("input", {
      placeholder: "buscar", value: busca,
      onChange: (e) =>
        setBusca(e.target.value),
    }),
    h("p", null,
      `${pacientes.length} pacientes`
      + ` · alto risco: ${alto}`),
    h("ul", null, vis.map((p) =>
      h("li", { key: p.id },
        h("b", null, p.nome), ` ${p.leito} `,
        h("input",
          { placeholder: "anotação" }),
        h("button",
          { onClick: () => alta(p.id) },
          "Alta")))));
}
  • useState guarda um valor entre renders e devolve a função que o troca. setPacientes não mexe no DOM: avisa o React de que o estado mudou.
  • h é o createElement do React. Ele devolve uma descrição do que deveria existir, não um nó. O JSX vira exatamente estas chamadas (capítulo 3).
  • key: p.id diz qual paciente cada linha representa.

A função Ala não sabe se roda pela primeira ou pela centésima vez: recebe o estado e devolve a tela. Quem compara a descrição nova com a anterior e aplica a diferença é o React.

1.7Declarativo, estado e reatividade

Declarativo é descrever o resultado para um estado e deixar o mecanismo decidir os passos. Estado da interface são os dados que, se mudarem, mudam o que aparece. Reatividade é a tela acompanhar o estado sem você escrever a atualização. No React ela é explícita: a tela só muda quando você chama o set do estado e o componente roda de novo. Vue, Svelte e Solid rastreiam sozinhos o que cada trecho da tela lê; são escolhas diferentes para o mesmo objetivo.

H+

O monitor de beira-leito

A enfermeira não redesenha a tela do monitor. Os sinais vitais mudam e o monitor atualiza a faixa que mudou. Os sinais vitais são o estado; a tela do monitor é a interface.

Onde a analogia para

O monitor real lê os sensores o tempo todo. O React não observa nada: só calcula a tela de novo quando alguém chama o set de um estado. Mudar uma variável comum não muda a tela.

1.8Biblioteca, não framework

O React transforma estado em interface. Rotas, busca de dados, build de produção e renderização no servidor vêm de outras ferramentas ou de um framework construído sobre ele.

Dado · react.dev, fev. 2025

2.4A tela e a API na mesma origem

A tela roda em :5173 e a API em :3000. Portas diferentes são origens diferentes para o navegador, o que traria CORS e regras de cookie entre sites. O proxy do Vite evita isso:

// O Vite serve a tela em :5173 e repassa para

export default defineConfig({
  plugins: [react()],
  server: {
    proxy: {
      "/api": "http://localhost:3000",
      "/health": "http://localhost:3000",

3.1O projeto do capítulo

Na tag cap03, a Ala B virou componentes com JSX e TypeScript, em src/features/pacientes. O cartão de cada paciente:

import type { Paciente } from "./tipos.ts";

interface Props {
  paciente: Paciente;
  onAlta: (id: string) => void;
}

export function CartaoPaciente(
  { paciente, onAlta }: Props,

  const { id, nome, leito } = paciente;

3.5O "Virtual DOM", com precisão

"Virtual DOM" é o apelido da árvore de elementos que cada render devolve. Ele não é uma cópia do DOM mantida em sincronia: é a descrição produzida por um render, comparada com a do render anterior. E não é sempre mais rápido que mexer no DOM à mão: no capítulo 1, imperativo e React fizeram o mesmo trabalho no DOM, e o React ainda executou componentes. 3.7Montar, atualizar, desmontar

Montar é aparecer numa posição: nós criados, estado no valor inicial. Atualizar é renderizar de novo no mesmo lugar. Desmontar é sair da árvore, levando nós e estado. Na medição completa, Ana Clara e Luzia voltam como mount quando a busca é limpa: tinham sido desmontadas.

O StrictMode testa a promessa chamando cada componente duas vezes em desenvolvimento, e é por isso que o Renderometro conta commits pelo Profiler em vez de somar uma variável no corpo do componente. 6.1O estado é uma foto

useState devolve o valor deste render e uma função para pedir o próximo. Chamar setX não muda x na linha seguinte; agenda um render novo, em que x terá o valor novo.

Por isso setTotal(total + 1) três vezes seguidas soma 1: as três chamadas leem o mesmo total da foto. Com a atualização funcional, setTotal((t) => t + 1), cada chamada recebe o resultado da anterior e a soma dá 3. Use essa forma sempre que o próximo valor depender do anterior.

6.2Guardar ou calcular

Antes de criar um estado, faça a pergunta do capítulo 5: dá para calcular? Total de pacientes, lista filtrada, paciente selecionado e "o formulário é válido?" são derivados: calculados a cada render, a partir de outro estado ou de props. Estado guardado em dobro precisa ser sincronizado à mão, e a sincronização é onde nascem os bugs. O capítulo 7 mostra o efeito que tenta fazer essa sincronização e por que ele é o erro mais comum de React.

Estado é o que o usuário fez ou o que o servidor disse. Todo o resto é derivado.

Efeitos: sincronizar com o mundo lá fora

Efeito não é "rodar código depois do render". É manter algo fora do React em dia com o estado, e desfazer isso quando o estado muda.

Terça, 16h. A médica procura "mar" na busca do prontuário. A tela mostra Maria Souza e, um instante depois, João Lima também. João não tem "mar" no nome. Ela recarrega, digita de novo, e o erro não volta.

Bug que aparece e some é quase sempre uma questão de tempo. Aqui, duas respostas do servidor chegaram fora de ordem, e a mais velha venceu. Este capítulo trata do único lugar do React feito para falar com o mundo lá fora, o efeito, e de como ele erra quando ninguém pensa em limpeza.

7.1As regras dos Hooks

Funções que começam com use são Hooks. O React guarda o estado deles pela ordem em que são chamados em cada render, por isso eles só podem ser chamados no nível de cima de um componente ou de outro Hook: nunca dentro de if, laço ou função comum. A regra react/rules-of-hooks do oxlint já vem como erro no template.

7.2Três tipos de lógica

Todo código de um componente cabe em um de três lugares, e só um deles é um efeito:

Total e lista filtrada são cálculo. Enviar a admissão é resposta a evento. Buscar o termo atual no servidor é sincronização. A diferença entre os dois últimos é a causa. O envio acontece porque alguém clicou; a busca precisa acontecer porque o termo é "mar", não importa como ele chegou a ser. Efeito é para o que precisa ficar em dia com o estado, seja qual for o caminho até ele.

H+

A enfermaria não faz o exame: pede ao laboratório, que fica fora dela. Se o médico troca o pedido antes do resultado sair, alguém precisa cancelar o pedido antigo, ou o resultado errado chega ao prontuário.

Onde a analogia para

O laboratório devolve um resultado só. Um efeito pode rodar e se desfazer muitas vezes por minuto, a cada mudança de dependência, e a limpeza roda sempre antes do próximo setup.

7.4A correção: limpar e cancelar

Na tag cap07, a busca virou um Hook personalizado, uma função comum cujo nome começa com use e que chama outros Hooks:

src/features/prontuario/useBuscaPacientes.tscap07
export function useBuscaPacientes(
  termo: string,
) {
  const [achados, setAchados] =
    useState<Achado[]>([]);

  useEffect(() => {
    if (!termo) return;
    const ctrl = new AbortController();
    const url = "/api/patients?q="
      + encodeURIComponent(termo)
      + location.search.replace("?", "&");
    fetch(url, { signal: ctrl.signal })
      .then((r) => r.json())
      .then((dados) => setAchados(dados))
      .catch((e: Error) => {
        // cancelado de propósito: não é erro
        if (e.name !== "AbortError") throw e;
      });
    return () => ctrl.abort();
  }, [termo]);

  return termo ? achados : [];
}

A função devolvida pelo efeito é a limpeza. O React a chama antes de rodar o efeito de novo e quando o componente sai da tela. Aqui ela cancela o pedido com AbortController: o fetch antigo é interrompido e a resposta dele nunca chega ao setAchados. O catch ignora só o cancelamento, que não é erro.

7.6StrictMode e a limpeza

Em desenvolvimento, o StrictMode monta cada componente, desmonta e monta de novo, rodando setup, limpeza e setup. É um teste automático da limpeza: se o efeito estiver certo, ninguém percebe; se faltar limpeza, aparecem dois pedidos, duas conexões, dois ouvintes de evento. A regra da documentação é que o usuário não deve conseguir distinguir uma montagem de setup, limpeza e setup. Não desligue o StrictMode para "resolver" o efeito duplicado: corrija a limpeza.

7.7useRef, useMemo e useCallback

O useRef apareceu no capítulo 6 como trava. Ele guarda um valor que sobrevive aos renders, muda na hora e não provoca render. Serve também para guardar um nó do DOM (ref={campo}), por exemplo para dar foco. Não leia nem escreva ref.current durante o render: o render precisa ser puro.

useMemo guarda o resultado de um cálculo e useCallback guarda uma função, ambos até uma dependência mudar. Eles existem por dois motivos: evitar repetir um cálculo caro e manter a mesma referência entre renders, para que um filho memoizado não renderize à toa ou um efeito não rode de novo.

Dado · react.dev, React Compiler 1.0 (out. 2025)

O compilador memoiza automaticamente. Para código novo, a documentação recomenda deixar a memoização com ele e usar useMemo e useCallback como válvula de escape, quando for preciso controle exato. O projeto liga o compilador no capítulo 16, com medição antes e depois.

Por isso o Mini-Prontuário ainda não usa nenhum dos dois; meça antes de usar. Por fim, o useEffectEvent, estável desde o React 19.2, cria uma função que o efeito chama e que sempre vê os valores atuais sem entrar nas dependências: por exemplo, registrar a busca em log com o nome de quem está logado sem refazer a busca quando a sessão muda.

Estrutura de projeto por funcionalidade

Comece simples; reorganize quando a dor aparecer; deixe uma ferramenta vigiar as fronteiras e um limite conter cada falha.

Quarta, 7h. A recepcionista abre o Mini-Prontuário, ainda sem entrar, e digita "ma" na busca. A tela inteira fica em branco: login, admissão, a Ala B, tudo.

Um erro numa busca derrubou seis painéis. No mesmo dia, a revisão acha o prontuário importando um componente de dentro da Ala. Dois sintomas de um projeto sem planta: ninguém escreveu quem fala com quem, nem até onde uma falha vai.

8.1Três estágios, e quando mudar

Estrutura não se escolhe no primeiro dia. Um arquivo só serve até você rolar mais do que lê; pastas por tipo (components/, hooks/) servem até uma mudança de tela tocar quatro pastas. A partir daí, organize por funcionalidade.

Na organização por funcionalidade, cada pasta de features/ guarda tudo de uma funcionalidade: componentes, hooks, tipos e testes. É a fatia vertical do Arquitetura em Tempos de IA, capítulo 4, aplicada à tela. Em volta delas ficam três pastas sem domínio: app/ monta a tela, compartilhado/ guarda peças que qualquer uma usa e api/ fala com o servidor.

8.4Uma porta só para a rede

Login, admissão, busca e status tinham cada um o seu fetch e a sua forma de ler a resposta. Agora todos passam por api/cliente.ts:

api/cliente.tscap08
export async function pedir<T>(
  caminho: string, o: Opcoes = {},
): Promise<T> {
  const temCorpo = o.corpo !== undefined;
  const r = await fetch(caminho, {
    method: o.metodo ?? "GET",
    signal: o.sinal,
    headers: temCorpo
      ? { "Content-Type": "application/json" }
      : undefined,
    body: temCorpo
      ? JSON.stringify(o.corpo) : undefined,
  });
  const tipo = r.headers.get("content-type");
  const json = tipo?.includes("json");
  const corpo: unknown = json
    ? await r.json() : await r.text();
  if (!r.ok) {
    throw new ErroHttp(r.status, corpo);
  }
  // o tipo T é promessa, não verificação
  return corpo as T;
}

Resposta fora de 2xx vira ErroHttp com status e corpo; quem chama recebe o dado ou uma exceção, nunca um Response para interpretar. O T é promessa ao TypeScript, não verificação: validar a resposta com Zod fica para o capítulo 14.

Para que ninguém volte a chamar fetch por fora, a regra no-restricted-globals do oxlint proíbe o global, com uma mensagem que aponta para pedir(); um bloco overrides a desliga em src/api/ e nos testes, que simulam a rede.

O .catch roda numa promessa, fora do render, e um erro ali não chega a nenhum limite. Por isso o hook guarda a falha em estado e a relança no render, na penúltima linha, onde o React sabe tratá-la. Quem a recebe é o limite de erro (error boundary):

compartilhado/LimiteDeErro.tsxcap08
…
export class LimiteDeErro
  extends Component<Props, Estado> {
  state: Estado = { falhou: false };

  static getDerivedStateFromError(): Estado {
    return { falhou: true };
  }
…
Dado · react.dev, Component

Limite de erro ainda é classe: não há Hook equivalente a componentDidCatch. Ele captura erros do render dos filhos, não de handlers, código assíncrono, SSR ou dele mesmo. Exceção: erro dentro de startTransition chega ao limite, e por isso uma action do React 19 que lança cai nele.

No render, quando falhou é verdadeiro, o limite mostra "algo falhou" e um botão "Tentar de novo" no lugar dos filhos. Onde pôr os limites é decisão de produto. Aqui, cada Painel embrulha os filhos num LimiteDeErro com o próprio título: a moldura que já existia virou a porta corta-fogo. A mesma busca, na tag cap08:

10.1Genérico e de domínio

O projeto já tem dois tipos de componente. CartaoPaciente sabe o que é um paciente; Painel não sabe o que mostra. O primeiro é de domínio e mora na feature; o segundo é genérico e mora em compartilhado/. O catálogo do projeto, o seu pequeno design system, é o segundo grupo com regras escritas.

H+

A maleta padronizada

Na maleta de instrumentos, cada peça tem um encaixe com a forma dela. Quem abre sabe na hora o que falta, e ninguém improvisa uma tesoura. A equipe não discute qual termômetro usar: discute o paciente.

Onde a analogia para

10.4A API de um componente

Todo componente do catálogo responde a quatro perguntas: que variantes existem, o que ele repassa ao elemento nativo, que padrão ele muda e onde entra o conteúdo. O Botao:

compartilhado/Botao.tsxcap10
// O <button> nativo com duas decisões já
// tomadas: o visual vem da variante, e o
// type é "button" (o nativo, num form,
// envia). No React 19, ref chega como prop.
export function Botao({
  variante = "primaria",
  type = "button",
  className,
  ...resto
}: Props) {
  const classes = [css.botao, css[variante],
    className].filter(Boolean).join(" ");
  return (
    <button type={type} className={classes}
      {...resto} />
  );
}

As variantes são poucas e com significado: primaria (uma por área), secundaria, perigo (ação sem volta) e texto (o nome clicável do paciente). ComponentProps<"button"> e o ...resto repassam tudo o que o nativo aceita: onClick, disabled, aria-pressed, o texto como children. O padrão que muda é o type: o <button> nativo dentro de um formulário é submit e envia, uma surpresa conhecida; no catálogo, envio é sempre explícito (type="submit").

No React 19, ref chega como prop comum; o forwardRef de tanto código antigo deixou de ser necessário e será descontinuado. O conteúdo entra por children. Moldura com dois buracos, corpo e ações, recebe um segundo ReactNode por prop (um slot), nunca dez props de configuração.

O Aviso junta uma decisão espalhada pelas telas: tom="erro" vira role="alert", lido na hora; tom="info" vira role="status", lido quando o leitor fica livre.

12.2Estado por fase, regras num lugar só

A primeira mudança não é de API, é de forma. Em vez de seis variáveis soltas, o estado é uma união discriminada: cada fase guarda só o que faz sentido nela.

admissao/assistente.tscap12
// Cada fase guarda só o que faz sentido
// nela: enviando não tem passo, admitido não
// tem dados. Estado impossível não compila.
export type Estado =
  | { fase: "editando"; passo: Passo;
      dados: Dados; erros: Erros;
      aviso?: string }
  | { fase: "enviando"; dados: Dados }
  | { fase: "admitido"; id: string };

export type Acao =
  | { tipo: "campo"; campo: keyof Dados;
      valor: string }
  | { tipo: "avancar" }
  | { tipo: "voltar" }
  | { tipo: "enviar" }
  | { tipo: "recomecar" }
  | Resposta;

"Enviando no passo 2" deixou de ser um bug possível: a fase enviando nem tem passo. As ações também são uma união, pelo campo tipo, e a Resposta do servidor entra nela sem conversão. O reducer recebe o estado atual e uma ação e devolve o próximo estado:

admissao/assistente.tscap12
export function assistente(
  e: Estado, a: Acao,
): Estado {
  switch (e.fase) {
    case "editando":
      return editando(e, a);
    case "enviando":
      if (a.tipo === "admitido") {
        return { fase: "admitido", id: a.id };
      }
      if (a.tipo === "recusado") {
        return { ...inicial(e.dados),
          erros: a.erros };
      }
      if (a.tipo === "falhou") {
        return { ...inicial(e.dados),
          passo: a.passo, aviso: a.msg };
      }
      return e;
    case "admitido":
      return a.tipo === "recomecar"
        ? inicial() : e;
  }
}

Aqui mora a diferença entre evento e transição. A tela despacha o evento "voltar" sempre que o botão é clicado; quem decide se isso muda alguma coisa é o reducer. Na fase enviando, voltar devolve o mesmo estado. O TypeScript estreita e em cada case: dentro de "enviando", e.passo nem compila.

12.5Quando usar, e até onde vai

useState basta para um valor isolado: o termo da busca, o modal aberto. Reducer começa a valer quando vários valores mudam juntos ou quando a pergunta é "nesta fase, isto vale?". Combinado com o capítulo 11, o despachar devolvido pelo useReducer é estável e cabe num contexto de ações: componentes distantes despacham eventos sem renderizar quando o estado muda.

O nativo tem limites: dado do servidor é outro problema (capítulo 14); muito estado compartilhado mudando com frequência pede assinatura seletiva, que Context não tem; e uma linha do tempo de ações pede ferramentas como as do Redux Toolkit, que usa a mesma ideia deste capítulo: estado, ação, função pura.

Regra · UI-16

Fluxo com fases e regras de transição mora num reducer puro, com o estado em união discriminada por fase. Ação fora da fase é ignorada pelo reducer, não só pelo botão. Verificação: assistente.test.ts (sem tela) e Assistente.test.tsx.

13.4Loader, erro e redirecionamento

O detalhe do paciente precisa do paciente para existir. Em vez de um efeito que busca depois de desenhar (capítulo 7), a rota tem um loader, que roda antes de a tela aparecer e recebe o signal da navegação:

prontuario/detalhe.tscap13
export async function carregarPaciente(
  { params, request }: LoaderFunctionArgs,
) {
  try {
    return await pedir<PacienteApi>(
      `/api/patients/${params.id}`,
      { sinal: request.signal });
  } catch (e) {
    if (!(e instanceof ErroHttp)) throw e;
    if (e.status === 401) {
      // entra e volta para cá
      const aqui = new URL(request.url);
      throw redirect("/entrar?volta="
        + encodeURIComponent(aqui.pathname));
    }
    if (e.status === 404) {
      throw data("Paciente não encontrado.",
        { status: 404 });
    }
    throw e;
  }
}

14.3Um cache com dono: TanStack Query

Estado remoto tem problemas que estado local não tem: tem outro dono, envelhece, é pedido por vários componentes ao mesmo tempo, precisa ser buscado de novo depois de uma mudança. O TanStack Query (5.106) resolve isso com um cache único, o QueryClient, onde cada dado tem uma chave.

api/consultas.tscap14
export const consultas = new QueryClient({
  defaultOptions: { queries: {
    // por 30 s o dado é fresco: quem pedir
    // a mesma chave usa o cache sem rede
    staleTime: 30_000,
    // repetir 401, 403, 404 não muda nada
    retry: (tentativas, e) => tentativas < 2
      && !(e instanceof ErroHttp
        && e.status < 500),
  } },
});

Por 30 segundos o dado é fresco: quem pedir a mesma chave recebe do cache, sem rede. Depois fica velho: ainda aparece, mas a próxima leitura busca de novo por baixo. Repetir pedido só vale para erro do servidor; um 404 repetido continua 404.

A busca usa useQuery com placeholderData: keepPreviousData: ao trocar de página, a lista velha fica na tela até a nova chegar, sem piscar vazio. 14.4Mudar: otimista, com volta

prontuario/consultas.tscap14
  return useMutation({
    mutationFn: (dados: Edicao) =>
      editarPaciente(id, dados),
    // Otimista: a tela muda antes da
    // resposta.
    onMutate: async (dados) => {
      await cliente.cancelQueries(
        { queryKey: chave });
      const antes =
        cliente.getQueryData(chave);
      cliente.setQueryData(chave,
        (p) => p && { ...p, ...dados });
      return { antes };
    },
    // Deu errado: volta ao que era.
    onError: (_e, _dados, ctx) =>
      cliente.setQueryData(chave, ctx?.antes),
    // Certo ou errado: o servidor tem a
    // palavra final, em todas as buscas.
    onSettled: () =>
      cliente.invalidateQueries(
        { queryKey: chaves.todos }),
  });

Antes de a requisição sair, onMutate cancela leituras em andamento daquela chave, guarda o valor anterior e escreve o novo no cache: a tela muda na hora. Se o servidor recusar, onError devolve o anterior. Dando certo ou errado, onSettled invalida ["pacientes"], e toda busca aberta pede de novo o que o servidor tem. No detalhe não há mais cópia: o componente lê do cache, e o formulário tem key={p.id}, para outro paciente ganhar outro formulário.

14.5Loader, Query ou os dois?

O loader responde "o que esta rota precisa para existir?" e decide redirecionamento e 404 antes da tela. O Query responde "quanto tempo esta cópia vale, e quem mais a usa?". Juntos, o loader enche o cache e a tela lê dele. Sem o Query, as actions do roteador revalidam os loaders, o que basta a apps com pouco dado compartilhado. O que não se faz é a terceira via: useEffect, fetch e useState em cada tela.

15.1Autenticar e autorizar, vistos da tela

Autenticar é saber quem é; autorizar é decidir o que essa pessoa pode fazer. No Crachá & Porta, as duas coisas foram construídas no servidor: senha com argon2, sessão no banco, cookie __Host-sessao com HttpOnly e SameSite=Lax, checagem de Origin contra CSRF e uma permissão exigida em cada rota. A tela não reimplementa nada disso: o navegador manda o cookie sozinho a cada fetch para a mesma origem, e ela pergunta e obedece. A primeira decisão é onde a credencial fica:

O React Router 8 tem middleware no modo de dados: uma função da rota que roda antes dos loaders das filhas, a cada navegação. As rotas protegidas ficam sob uma rota sem caminho com middleware: [exigirSessao] e handle: { protegida: true }:

app/protecao.tscap15
// Roda antes dos loaders das rotas filhas:
// sem sessão, ninguém pede o paciente.
export const exigirSessao:
  MiddlewareFunction = async (
    { request },
  ) => {
    const u = await consultas
      .ensureQueryData(consultaSessao);
    if (!u) {
      throw redirect(
        paraLogin(new URL(request.url)));
    }
  };

Na primeira navegação, ensureQueryData pergunta ao servidor; nas seguintes, responde do cache. Recarregar zera o cache e a pergunta volta ao servidor: a sessão sobrevive ao F5 sem nada guardado no navegador.

15.5401 e 403 não são o mesmo erro

O middleware só roda na navegação. Se a sessão acaba com a tela parada, a próxima consulta ou mutação recebe 401. O cache tem um ponto só para isso:

api/consultas.tscap15
// Ninguém entrou: quem lê a sessão (o
// Layout, o middleware) fica sabendo.
const semSessao = () =>
  consultas.setQueryData(CHAVE_SESSAO, null);

// Sair: a tela esquece tudo o que viu. Só
// depois de deixar as rotas protegidas, ou
// as telas abertas pediriam tudo de novo.
export function esquecerSessao() {
  consultas.removeQueries({ predicate: (q) =>
    q.queryKey[0] !== CHAVE_SESSAO[0] });
  semSessao();
}

// 401 numa consulta ou mutação: o servidor
// encerrou a sessão com a tela aberta.
function se401(e: Error | null) {
  if (e instanceof ErroHttp
    && e.status === 401) semSessao();
}

se401 fica no onError do QueryCache e no onSettled do MutationCache, que roda depois de a edição otimista devolver o nome anterior. Gravar null avisa o Layout, que conhece a rota atual: se ela tem handle.protegida, ele devolve <Navigate to={paraLogin(local)} />.

Servidor, cliente e a fronteira entre eles

Onde cada pedaço da tela é montado, e o que atravessa a fronteira. Nada atravessa de graça.

Até aqui, o servidor mandava um HTML quase vazio, e a tela nascia no navegador. Numa 4G lenta, a recepcionista espera um segundo e meio pelo CNS de Maria. Montada no servidor, a mesma ficha aparece em menos de meio segundo, e cobra o próprio preço.

17.1Quatro maneiras de montar a mesma tela

CSR (no cliente) é o que este livro fez: o navegador baixa o JavaScript, pede os dados e desenha. SSR (no servidor) monta o HTML com os dados a cada pedido; o navegador mostra na hora e depois hidrata: o React percorre o HTML pronto, liga os eventos e assume a tela. SSG monta o HTML no build, uma vez para todos; a geração incremental o refaz de tempos em tempos. O streaming manda a casca primeiro e, no mesmo HTML, as partes que dependem de dados, quando ficam prontas.

17.3Server Components

No Next, páginas e componentes são Server Components por padrão. Rodam só no servidor, podem ser async, leem cookie e banco, e mandam ao navegador só o resultado: HTML na primeira carga e um formato serializado (o RSC payload) nas navegações seguintes. 17.4'use client' marca uma fronteira

O botão Copiar CNS precisa de estado e de clique, então mora num arquivo que começa com "use client". A diretiva não marca um componente, marca uma fronteira no grafo de módulos: tudo o que esse arquivo importa vai junto para o navegador. Por isso ela fica no ponto mais baixo da árvore. O que atravessa a fronteira são props serializáveis: texto, número, objeto simples, data, JSX já renderizado. Função, não, a não ser uma Server Function ("use server"). Um Server Component pode entrar num componente cliente como children, já renderizado.

17.7A fronteira é uma porta

Server Functions transformam um pedido HTTP numa chamada de função no servidor. A fronteira é uma porta HTTP, e foi por ela que veio a falha mais grave do ecossistema em 2025.

Dado · as falhas de dezembro de 2025

Em 3 de dezembro, o React publicou a CVE-2025-55182 (CVSS 10,0): um pedido forjado, sem autenticação, executava código no servidor por uma falha na decodificação dos dados enviados a Server Functions. Afetava react-server-dom-* 19.0 a 19.2.0, mesmo em apps sem Server Functions próprias; corrigida em 19.0.1, 19.1.2 e 19.2.1. Em 11 de dezembro vieram negação de serviço (CVSS 7,5) e exposição do código-fonte de Server Functions (CVSS 5,3), com correção definitiva em 19.0.4, 19.1.5 e 19.2.4. Apps React sem servidor não foram afetados.

Três lições. Server Function valida entrada e permissão como qualquer rota, porque é uma. Segredo não fica escrito no código, nem no servidor. E o framework entra na rotina de atualização com a urgência da API.

Regras do laboratório Next

Componente é do servidor até precisar de estado ou evento; "use client" só na ilha. Render igual nos dois lados. Módulo com dados ou configuração do servidor começa com import "server-only". Server Function valida como rota.

O agente escreve. Você decide o escopo, quebra em passos, exige prova a cada um e assina a entrega.

19.1O pedido, e o que é de verdade

O pedido cabe em duas frases. Painel em /atendimentos, com os atendimentos que a pessoa pode ver. 19.2Doze passos, um commit cada

O tamanho de um passo é o que você consegue revisar com calma: um diff que cabe na cabeça, um portão verde no fim. Entre um passo e outro, a sessão do agente recomeça com o contexto escrito, não com a conversa anterior.
