Next.js: visão geral e próximo livro

Um mapa, não um curso. O suficiente para decidir quando usar, e para saber o que vem depois.

O React desenha a tela. O Next.js decide onde e quando ela é desenhada, cuida de rotas, dados e cache, e põe um servidor ao lado do seu código. Aqui vai o mapa, no laboratório do capítulo 17, e uma tabela de decisão.

18.1O que o Next acrescenta ao React

PeçaO que é no Next 16
RotasPastas em app/: page, layout, loading, error, not-found. Layout aninhado não renderiza de novo ao trocar de página
RenderizaçãoServer Components por padrão, streaming com <Suspense>, casca estática com partes dinâmicas

○ é HTML pronto no build; /sobre também, com prazo de um dia, porque usa "use cache". ◐ é a ficha: casca pronta, e a parte que lê o cookie chega em streaming. ƒ roda a cada pedido. É a figura 17.1, impressa pelo framework para cada rota.

{{BLOCO:next@cap18:proxy.ts|linhas=4-18|rotulo=proxy.ts}}
medicoes/cap18.py · Medido
{{SAIDA:c18-mapa.txt|linhas=18-20|destaque=307;200}}

Sem cookie, o proxy responde 307 antes de renderizar, como o middleware do capítulo 15. Com um cookie inventado, deixa passar: só confere se o cookie existe. Quem recusa é a API, dentro da ficha, e como a resposta já tinha começado com 200 e a casca, o redirecionamento chega dentro do HTML. A documentação do Next chama o proxy de checagem otimista, que não deve ser a autorização. Quem decide é quem guarda os dados.

18.3Dados, cache, autenticação e implantação

Dados e cache. Com Cache Components, ligado nos projetos novos do Next 16, nada vai para o cache sem pedido. Dado que depende do pedido (cookie, parâmetro) fica num <Suspense> e chega em streaming; o que pode ser reaproveitado leva "use cache" e um prazo (em /sobre: cacheLife("days")), e uma mutação invalida a etiqueta. É o raciocínio do capítulo 14, no servidor.

Autenticação. As regras do capítulo 15 continuam: cookie HttpOnly, checagem no servidor, perto dos dados, numa camada de acesso a dados que toda leitura atravessa; o proxy é atalho. Implantação. Servidor Node (next start) ou contêiner suportam tudo; a exportação estática perde streaming, Server Functions e proxy. A SPA do Vite é só arquivos; um Next completo precisa de um processo rodando.

18.4Vite SPA ou Next.js

A escolha não é de moda. Três perguntas resolvem quase todos os casos. A primeira visita precisa mostrar dados rápido, ou ser indexada? Já existe uma API separada, com dono? Quem opera um servidor Node em produção? Com "não", "sim" e "ninguém", a SPA basta. O resto do livro vale nos dois. Cinco cenários:

CenárioEscolha e motivo
Sistema interno com login (o Mini-Prontuário)SPA. Ninguém indexa; a API já existe; menos peças para operar
Site público do hospital, com notícias e serviçosNext. HTML pronto para buscadores e para a primeira visita; SSG com prazo
Portal do paciente no celular, com rede ruimNext. O dado vem no HTML; medido no capítulo 17: CNS em 375 ms contra 1486 ms
Painel de leitos em tempo realSPA. Quase tudo é interação e atualização no cliente
Produto novo, time pequeno, sem backend separadoNext. Tela e servidor num projeto. Cada Server Function é uma rota a validar (17.8)

18.5O próximo livro

O Next.js ganha um livro próprio na série, no mesmo formato: um projeto que cresce, medições e agentes sob portões. Ele começa onde este termina e pressupõe:

  • onde cada estado mora; efeito só para sincronizar (caps. 6 a 14)
  • rotas aninhadas, loader e redirecionamento interno (cap. 13)
  • sessão em cookie, 401 diferente de 403, esconder não é proibir (cap. 15)
  • teste pela tela, rede simulada na fronteira, uma jornada E2E (cap. 16)
  • fronteira servidor/cliente, hidratação e server-only (cap. 17)
