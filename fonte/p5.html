04

Componentes, JSX e composição

Peças pequenas que se encaixam. Nem toda repetição pede um componente, e nenhum componente nasce dentro de outro.

Quinta, 15h. A tela da Ala B ganhou resumo por risco, um selo colorido em cada paciente e um aviso para busca sem resultado. Tudo foi parar dentro de Ala. Desde então, a cada letra digitada na busca, as anotações somem.

O código novo não tem erro de lógica. Tem um erro de forma: um componente foi definido no lugar errado. Este capítulo trata de como dividir uma tela em componentes, e dos dois jeitos de errar nisso.

4.1Um componente é uma função

Um componente é uma função que recebe um objeto, as props, e devolve JSX. Poucas regras sustentam tudo:

RegraExemplo
Nome com maiúscula; minúscula é tag HTML<CartaoPaciente /> × <li>
Uma raiz, ou um fragmento<>…</> agrupa sem criar nó
Atributos em camelCaseclassName, onClick, aria-label fica igual
Chaves para expressões{pacientes.length}; if não cabe, ternário cabe
Toda tag fecha<input />, <br />

4.2O componente que cresceu demais

Na tag cap04-antes, a Ala tem 74 linhas e faz tudo. No meio dela, para "organizar", alguém extraiu a linha da lista para um componente Linha, escrito dentro de Ala:

{{BLOCO:cap04-antes:src/features/pacientes/Ala.tsx|linhas=25-41|rotulo=Ala.tsx · Linha, dentro de Ala}}

Parece inofensivo, e o código usa key={p.id} corretamente. O problema é a regra do capítulo 3: tipo diferente na mesma posição, o React desmonta e monta de novo. A cada render de Ala, a função Linha é criada outra vez. É uma função nova, logo um tipo novo. O React não tem como saber que é "a mesma Linha": desmonta todas as linhas, com o que havia nelas, e monta outras.

4.3Composição

A correção, na tag cap04, não é só tirar Linha de dentro de Ala. É dividir a tela pelo que cada pedaço é para quem usa: o resumo, a busca, a lista, o cartão, o selo.

As bandejas do carrinho

O carrinho de procedimentos não tem um compartimento para cada combinação de material. Tem bandejas padronizadas que se encaixam de jeitos diferentes. O Painel é o encaixe; o que vai dentro muda a cada uso.

Onde a analogia para

Bandeja física tem tamanho fixo. A composição do React aninha sem limite: um Painel dentro de outro, uma lista dentro de um painel. O custo de aninhar é só de leitura, não de desempenho.

4.4Composição, duplicação e abstração prematura

Dividir demais também é erro. O sintoma é o componente genérico que tenta servir a todos os casos:

Abstração prematura

<Cartao tipo="paciente" mostrarSelo mostrarBotaoAlta titulo={…} subtitulo={…} … />: dez props booleanas, um if para cada combinação, e ninguém sabe qual combinação a tela usa.

Composição

Componentes de domínio pequenos (CartaoPaciente, SeloRisco) e uma moldura que recebe children. Cada um tem um motivo para mudar.

O projeto adota três critérios, escritos em docs/UI.md para que o agente os siga também:

docs/UI.md · quando extrair um componente
  • Um trecho com nome próprio na conversa do usuário ("o resumo").
  • Um trecho repetido pela terceira vez. Na segunda, copie e espere.
  • Nunca para "deixar genérico" antes de existir o segundo uso real.
Ponte · Dev de IA, cap. 6

O docs/UI.md também fixa um componente por arquivo, nomes em PascalCase e props numa interface Props. O Dev de IA explica por que esse arquivo reduz retrabalho e como mantê-lo curto.

4.5Com agentes de IA

Armadilha de IA

Os agentes erram para os dois lados. Pedidos de "mais uma funcionalidade" sem contexto tendem a crescer o componente que já existe até virar um componente-deus, muitas vezes com um componente auxiliar definido lá dentro, exatamente o defeito deste capítulo. Pedidos de "deixe reutilizável" tendem a produzir o cartão genérico com dez props. O docs/UI.md e a UI-02 cortam os dois.
