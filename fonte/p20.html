19

A entrega com agentes, do plano ao PR

O agente escreve. Você decide o escopo, quebra em passos, exige prova a cada um e assina a entrega.

Falta a parte clínica do Mini-Prontuário: o profissional precisa ver os atendimentos dele e prescrever. É a última entrega do livro, feita como se faz no trabalho: um plano aprovado, doze passos com um commit cada, um teste vermelho que conta uma história, uma revisão que acha um defeito e um PR que se lê sem abrir o código.

19.1O pedido, e o que é de verdade

O pedido cabe em duas frases. Painel em /atendimentos, com os atendimentos que a pessoa pode ver. Ficha em /atendimentos/:id, com as prescrições, o formulário de prescrição para quem prescreve e o botão Finalizar para o autor. Nada é simulado na tela: a API cap19 é a mesma dos capítulos 14 e 15, com sessão em cookie HttpOnly, permissões por papel e as regras clínicas (só o autor vê o motivo; prescrever exige rx:create, ser o autor, atendimento aberto e plantão). Os dados são fictícios, num banco em memória, e a rede só é simulada nos testes de tela, com o MSW.

19.2Doze passos, um commit cada

O tamanho de um passo é o que você consegue revisar com calma: um diff que cabe na cabeça, um portão verde no fim. Entre um passo e outro, a sessão do agente recomeça com o contexto escrito, não com a conversa anterior.

git log cap16..cap19 mostra treze commits: os doze passos e, antes deles, dev:https, que arruma o ambiente para o Safari (19.9). O histórico é a primeira evidência do PR. Quem revisa pode fazer git checkout em qualquer passo e encontrar o projeto funcionando, com o portão verde.

A passagem de plantão

A equipe se reúne, olha o quadro e divide o trabalho em cartões pequenos. O robô auxiliar leva e busca, rápido e sem cansar. Cada cartão só muda de coluna com o item conferido, e quem assina o plantão é a pessoa responsável, não o robô.

Onde a analogia para

O robô do hospital não inventa um remédio quando não acha a gaveta. O agente pode inventar uma rota, uma permissão ou um teste que passa por motivo errado, e diz isso com a mesma confiança. E não lembra do plantão anterior: o que ele sabe está nos arquivos que você mandou ler.

19.3Preparar: contexto e plano

Passo 01. O agente lê o código da API, em modo de plano, e escreve em docs/API.md o contrato de atendimentos e prescrições: rotas, permissões, o que só o autor recebe. Ler, não supor: a documentação é o que os passos seguintes usam como verdade. Passo 02. O plano, em docs/PLANO-cap19.md, com escopo, fora de escopo, riscos e oito critérios, cada um com o teste ou o instrumento que o verifica:

#Critério · como se verifica

A3Prescrever só com rx:create e aberto · teste; porta-dos-fundos

O plano é o único passo sem código, e o único que só você aprova. Um critério sem verificação ("a tela deve ser intuitiva") não entra: o agente não tem como saber quando terminou, e você também não.

19.4Construir: estrutura, peças e permissões

Os passos 03 a 07 aplicam o livro inteiro, e cada um termina com o portão verde. Quatro decisões merecem registro no PR:

  • Estrutura (03). A ficha mostra o nome do paciente, que é dado da feature de prontuário. Feature não importa feature (UI-08): a consulta do paciente subiu para src/api/, e o fronteiras confirmou.
  • Componentes (04). Lista, ficha e formulário só recebem props. O formulário valida como a API e não se limpa antes da resposta: se a API recusar, o texto fica.
  • Serviços (05). Prescrição sem atualização otimista. É registro clínico: aparece quando o servidor confirmou com 201, não antes.
  • Rotas (06). Loader com ensureQueryData, sob o middleware da sessão; 404 vira mensagem.

O passo 07 é o mais delicado. A sessão diz o que o papel pode fazer em geral: rx:create. Mas prescrever depende também do contexto (ser o autor, atendimento aberto, estar de plantão), que só a API confere. A tela usa o que sabe e trata o resto como resposta possível:

{{BLOCO:cap19:src/features/atendimentos/Ficha.tsx|linhas=51-73|reticencias=sim|rotulo=features/atendimentos/Ficha.tsx}}

Autoria e status a tela conhece (vieram no atendimento); plantão, não. Por isso o botão aparece para a Dra. Ana às 23h, e a API recusa. Esconder o botão por horário seria copiar uma regra do servidor que pode mudar sem a tela saber. Duas linhas de código merecem nota: o key do formulário muda quando a lista cresce, e isso limpa os campos depois do 201 sem efeito nenhum (capítulo 3); e o 403 vira o aviso "A API recusou a prescrição: ela confere autoria, status e plantão.", sem dizer qual regra falhou, porque a API não conta.

Armadilha de IA · o atalho para o verde

Com teste vermelho, o agente costuma propor o caminho mais curto: dar rx:read à recepção na API falsa, trocar findByRole por algo que sempre acha, ou envolver o loader num try/catch que engole o 403. Todos deixam o portão verde e a tela quebrada para a recepção de verdade. A regra do passo 09: reproduzir no navegador, com a API real, antes de mudar uma linha.

19.6Depuração: a recepção derrubava a ficha

Reproduzir é o primeiro passo. O roteiro entra como Carla, abre /atendimentos/e1 com a API real e anota a rede e a tela, antes e depois:

medicoes/cap19.py · Medido
{{SAIDA:c19-depuracao.txt|linhas=1-8|destaque=→ 403;Algo falhou ao abrir esta página.}}

{{SAIDA:c19-depuracao.txt|linhas=10-21|destaque=Motivo visível só para o profissional responsável.;Só quem prescreve vê.}}

A causa estava no loader. Ele pedia atendimento e prescrições em paralelo, com Promise.all; a recepção não tem rx:read, a API respondeu 403, a promessa inteira falhou e o erro da rota tomou o lugar da ficha. A tela não estava errada para a Dra. Ana, que tem a permissão. Estava errada para quem não tem, e ninguém tinha testado com esse papel até o passo 08. A correção pergunta antes de pedir:

{{DIFF:cap19-passo08:cap19:src/features/atendimentos/rota.ts}}

O segundo vermelho tinha outra causa, achada no mesmo roteiro: a API não manda o motivo para quem não é autor (é dado clínico), e a ficha mostrava o rótulo "Motivo" com nada embaixo. Um vazio não diz se o dado não existe, se falhou ou se é proibido. Agora a ficha diz qual dos três, e "Só quem prescreve vê." ocupa o lugar das prescrições. Uma mudança por vez, cada uma com o teste que a pedia.

Regra · UI-26

Permissão diz o que o papel pode fazer em geral; o contexto (autoria, status, plantão) só a API confere. A tela mostra a ação pela permissão e pelas regras que conhece, trata o 403 no lugar e não pede leitura que o papel não tem: o loader confere a permissão antes.

19.7Revisão: contexto novo, checklist adversarial

Quem escreveu o código não é um bom revisor dele, pessoa ou agente: lê o que quis escrever. O passo 10 abre uma sessão nova, sem a conversa dos passos anteriores, e entrega o diff inteiro com o checklist. O ideal é outro fabricante, para não repetir os mesmos pontos cegos.

19.9O ambiente: o Safari e o cookie

O plano deixou uma conferência para o laboratório: o cookie __Host-sessao exige Secure, e a tela roda em http://localhost. Chromium trata localhost como contexto seguro e aceita. Para conferir o motor do Safari, o roteiro repete o login no WebKitGTK, que é o WebKit com a pilha de rede do GTK:

medicoes/cookie_navegadores.py · Medido
{{SAIDA:c00-cookie-navegadores.txt|linhas=1-3}}
{{SAIDA:c00-cookie-navegadores.txt|linhas=5-7|destaque=401;não}}

{{SAIDA:c00-cookie-navegadores.txt|linhas=10-12|destaque=200;sim}}

Em http, o login responde 200, o WebKit descarta o cookie e a sessão some no pedido seguinte. Afrouxar o cookie da API em desenvolvimento faria o laboratório divergir da produção; a escolha foi o inverso, levar a tela para HTTPS local. npm run dev:https sobe o Vite em https://localhost:5173 com certificado autoassinado, e a API cap19 aceita essa origem. O Firefox ficou sem teste: o ambiente do livro não conseguiu baixá-lo.

19.10Documentação e PR

O passo 12 atualiza o que o próximo agente vai ler (INVARIANTES.md com a UI-26, docs/UI.md, README) e escreve o PR em docs/PR-cap19.md. A regra do PR é a do capítulo 16, em ponto maior: cada critério do plano aponta para uma evidência que alguém pode rodar de novo. A1 a A6 são os seis testes, com o número do critério no nome; A3 tem também o porta-dos-fundos; A5, a saída do plantão; A7 e A8, as saídas do portão e do axe.

O IA.md ganha uma entrada: ferramenta e versão, o que foi verificado, o que foi recusado (o cookie afrouxado) e o limite da revisão. O PR diz também como revisar: git log cap16..cap19, depois git checkout cap19-passo08 && npm test para ver o vermelho que o passo 09 resolve.
